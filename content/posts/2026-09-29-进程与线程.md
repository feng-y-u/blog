# Python 进程与线程

多任务可以由**多进程**完成，也可以由一个进程内的**多线程**完成。这篇按这条线整理：怎么开进程 → 进程之间怎么传数据 → 怎么开线程 → 线程共享数据为什么要加锁 → 为什么 Python 的多线程吃不到多核 → 最后是怎么选。

## 多进程

### fork()：Unix/Linux 下的进程复制

Unix/Linux 操作系统提供了一个 `fork()` 系统调用，它非常特殊：**调用一次，返回两次**——因为操作系统自动把当前进程复制了一份，然后分别在父进程和子进程内返回。

- **子进程永远返回 `0`**；
- **父进程返回子进程的 ID**：一个父进程可以 `fork()` 出很多子进程，父进程要记下每个子进程的 ID；
- 子进程只需要调用 `getppid()` 就可以拿到父进程的 ID。

Python 的 `os` 模块中就包括 `fork`：

```python
import os

print('Process (%s) start...' % os.getpid())
# Only works on Unix/Linux/macOS:
pid = os.fork()
if pid == 0:
    print('I am child process (%s) and my parent is %s.' % (os.getpid(), os.getppid()))
else:
    print('I (%s) just created a child process (%s).' % (os.getpid(), pid))
```

> **注意**：Windows 没有 `fork` 调用（我这台就是 Windows），这段代码只能在 Unix/Linux/macOS 上跑。Windows 上要用下面的 `multiprocessing` 模块。

### multiprocessing：跨平台的写法

```python
from multiprocessing import Process
import os

# 子进程要执行的代码
def run_proc(name):
    print('Run child process %s (%s)...' % (name, os.getpid()))

if __name__ == '__main__':
    print('Parent process %s.' % os.getpid())
    p = Process(target=run_proc, args=('test',))
    print('Child process will start.')
    p.start()      # 子进程启动
    p.join()       # 父进程等待子进程结束
    print('Child process end.')
```

实测输出（PID 每次运行都不同）：

```text
Run child process test (237592)...
Parent process 248760.
Child process will start.
Child process end.
```

创建子进程时，需要传入一个**执行函数**和**函数的参数**，创建一个 `Process` 实例，再用 `start()` 方法启动；`join()` 方法可以等待子进程结束后再继续往下运行。

> **注意 `target` 要传函数对象，不能带括号**：
> `target=run_proc` 是"把函数交给子进程去执行"；写成 `target=run_proc('test')` 会**在当前进程里立刻调用**这个函数，然后把返回值（`None`）当 target。
>
> **`if __name__ == '__main__':` 这个保护在 Windows 上必须写**：Windows 用 spawn 方式创建进程，子进程会重新 import 主模块；不写保护就会不断重生子进程。我自己写基准脚本时忘了加，结果无限派生、刷屏报错：
> `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase.`

### 进程池 Pool

要启动大量子进程，可以用**进程池**的方式批量创建：

```python
from multiprocessing import Pool
import os, time, random

def long_time_task(name):
    print('Run task %s (%s)...' % (name, os.getpid()))
    start = time.time()
    time.sleep(random.random() * 3)     # 模拟一个耗时的操作，随机休眠 0~3 秒
    end = time.time()
    print('Task %s runs %0.2f seconds.' % (name, (end - start)))

if __name__ == '__main__':
    print('Parent process %s.' % os.getpid())
    p = Pool(processes=4)                        # 创建进程池
    for i in range(5):
        p.apply_async(long_time_task, args=(i,))  # 异步提交任务，哪个进程空闲哪个执行
    print('Waiting for all subprocesses done...')
    p.close()   # 关闭进程池，表示不能再往池里添加任务
    p.join()    # 等待所有子进程执行完毕，必须放在 close() 之后
    print('All subprocesses done.')
```

实测输出（注意任务 1 和任务 4 用的是同一个进程号，说明进程被复用了）：

```text
Run task 0 (244040)...
Task 0 runs 1.20 seconds.
Run task 3 (244540)...
Task 3 runs 1.40 seconds.
Run task 2 (239472)...
Task 2 runs 1.43 seconds.
Run task 1 (246620)...
Task 1 runs 0.66 seconds.
Run task 4 (246620)...
Task 4 runs 2.90 seconds.
Parent process 254116.
Waiting for all subprocesses done...
All subprocesses done.
```

- `Pool` 的**默认大小是 CPU 的核数**（我本机 `os.cpu_count()` 是 `16`）；
- 池里只有 4 个进程，却有 5 个任务，所以第 5 个任务要等前面某个跑完才能开始——这也是 `Task 4` 耗时最长（多等了 1.4 秒）的原因。

### 子进程：subprocess

前面创建的子进程都是**把自身复制一份**，但很多时候子进程是一个**外部进程**。`subprocess` 模块可以启动一个子进程，并控制它的输入和输出：

```python
import subprocess

print('$ nslookup www.python.org')
r = subprocess.call(['nslookup', 'www.python.org'])   # 相当于在终端运行这条命令
print('Exit code:', r)                                # 退出码，0 表示执行成功
```

需要给子进程**输入**时（比如 `nslookup` 需要在运行时敲命令），可以用 `communicate()`：

```python
import subprocess

print('$ nslookup')
p = subprocess.Popen(['nslookup'], stdin=subprocess.PIPE,
                     stdout=subprocess.PIPE, stderr=subprocess.PIPE)
output, err = p.communicate(b'set q=mx\npython.org\nexit\n')   # b 表示字节串
print(output.decode('gbk', errors='ignore'))
print('Exit code:', p.returncode)
```

- `Popen()` 返回一个 `Popen` 对象，表示子进程；把 `stdin`、`stdout`、`stderr` 重定向到管道后，Python 就能和子进程直接通信；
- `communicate()` 会等子进程执行结束，返回 `(stdout, stderr)` 元组；
- 打印时要把字节串解码成字符串——Windows 的 `nslookup` 输出是 GBK 编码，所以这里用 `decode('gbk')`。

### 进程间通信：Queue

同一个变量在**多个进程**里各有一份拷贝，互不影响，所以进程之间必须显式通信。`multiprocessing` 模块包装了底层的通信机制，提供了 `Queue`、`Pipes` 等方式。

以 `Queue` 为例：`write()` 负责生产数据，通过 `q.put()` 放进队列；`read()` 负责消费数据，通过 `q.get()` 从队列取出：

```python
from multiprocessing import Process, Queue
import os, time, random

# 写数据进程执行的代码:
def write(q):
    print('Process to write: %s' % os.getpid())
    for value in ['A', 'B', 'C']:
        print('Put %s to queue...' % value)
        q.put(value)
        time.sleep(random.random())

# 读数据进程执行的代码:
def read(q):
    print('Process to read: %s' % os.getpid())
    while True:
        value = q.get(True)      # q.get(True) 表示队列为空时一直等待，直到有数据
        print('Get %s from queue.' % value)

if __name__ == '__main__':
    q = Queue()                                  # 父进程创建 Queue，并传给各个子进程
    pw = Process(target=write, args=(q,))
    pr = Process(target=read, args=(q,))
    pw.start()                                   # 启动写入子进程
    pr.start()                                   # 启动读取子进程
    pw.join()                                    # 等待 pw 结束
    pr.terminate()                               # pr 是死循环，无法等待其结束，只能强行终止
```

实测输出：

```text
Process to read: 248744
Process to write: 236116
Put A to queue...
Get A from queue.
Put B to queue...
Get B from queue.
Put C to queue.
Get C from queue.
```

> **踩坑记录**：第一次跑的时候只看到 `write` 进程的输出，`read` 进程一行都没有。原因是**子进程被 `terminate()` 强行终止时，它 stdout 里缓冲的内容直接丢了**。加上环境变量 `PYTHONUNBUFFERED=1`（或用 `python -u` 运行）让子进程不缓冲，输出才完整——上面这份就是加了这个变量之后的结果。

## 多线程

多任务可以由多进程完成，也可以由**一个进程内的多线程**完成：

- 进程是由若干线程组成的，**一个进程至少有一个线程**；
- 线程是操作系统直接支持的执行单元；
- Python 的标准库提供了两个模块：`_thread` 和 `threading`。`_thread` 是低级模块，`threading` 是高级模块、对 `_thread` 做了封装，绝大多数情况下只用 `threading` 就够了。

### 启动一个线程

启动一个线程，就是把一个函数传入并创建 `Thread` 实例，然后调用 `start()` 执行：

```python
import time, threading

def loop():
    print('thread %s is running...' % threading.current_thread().name)
    n = 0
    while n < 5:
        n = n + 1
        print('thread %s >>> %s' % (threading.current_thread().name, n))
        time.sleep(1)
    print('thread %s ended.' % threading.current_thread().name)

print('thread %s is running...' % threading.current_thread().name)
t = threading.Thread(target=loop, name='LoopThread')
t.start()
t.join()
print('thread %s ended.' % threading.current_thread().name)
```

实测输出（每秒一行，共 5 秒）：

```text
thread MainThread is running...
thread LoopThread is running...
thread LoopThread >>> 1
thread LoopThread >>> 2
thread LoopThread >>> 3
thread LoopThread >>> 4
thread LoopThread >>> 5
thread LoopThread ended.
thread MainThread ended.
```

- `join()` 让当前线程暂停，等子线程执行完毕后再继续往下执行；
- 任何进程默认就会启动一个线程，称为**主线程**，主线程又可以启动新的线程；
- `current_thread()` 永远返回当前线程的实例：主线程名字为 `MainThread`，子线程名字在创建时指定，不指定就自动命名为 `Thread-1`、`Thread-2`。

### Lock：共享变量与数据竞争

多进程和多线程最大的不同在于：

- **多进程**中，同一个变量各自有一份拷贝存在于每个进程中，互不影响；
- **多线程**中，所有变量都由所有线程**共享**。

如果有两个线程并发执行、并且共同修改一个共享变量，就会出现**数据竞争**。解决方法是给这段代码上一把**锁**：某个线程开始执行时先获得锁，其他线程只能等锁被释放；锁只有一个，无论多少线程，同一时刻只有一个线程持有锁。

```python
balance = 0
lock = threading.Lock()      # 创建锁对象

def run_thread(n):
    for i in range(100000):
        lock.acquire()       # 获取锁
        try:
            change_it(n)
        finally:
            lock.release()   # 改完了一定要释放锁
```

> **为什么要用 `try...finally`**：如果临界区里抛了异常，`release()` 就不会执行，锁永远不释放，剩下的线程就全卡死了。放进 `finally` 能保证锁一定被释放。

不过这里有个**必须说清楚的坑**。教程里那个经典例子是：

```python
balance = 0

def change_it(n):
    global balance
    balance = balance + n
    balance = balance - n
```

它想说明"不加锁时 `balance` 会变成非 0"。但我实测下来——**无论加不加锁，`balance` 都是 0**：

```text
【不加锁】balance = 0        # 10 万次循环
【不加锁】balance = 0        # 100 万次循环
【临界区停留 1ms · 不加锁】balance = 0
```

原因有两个：

1. **这个例子的加减是"纯加法配对"**：整个程序对所有操作求和，`+5 -5 +8 -8` 无论以什么顺序交错，结果都是 0。它在数学上就不可能跑出非 0，除非**某次"读-改-写"被中途打断、丢掉了一次更新**；
2. 而在现代 CPython（3.13）里，GIL 的切换点并不落在这条很短的"读-改-写"序列中间，所以连"丢更新"都很难发生。

要**真的复现**数据竞争，得把"读"和"写"之间的窗口撑开，比如中间插一段可切换的循环，并把线程切换间隔调小：

```python
import sys, threading
sys.setswitchinterval(0.000001)      # 1 微秒就检查一次线程切换

balance = 0
COMMITS = 3000

def change_it(n):
    global balance
    tmp = balance          # 读
    for _ in range(200):   # 读和写之间插入一段可切换的循环
        pass
    balance = tmp + n      # 改 + 写
```

实测结果（两个线程分别加 5 和 8，各 3000 次，正确结果应为 `3000 × 13 = 39000`）：

```text
【切换间隔 1μs · 不加锁】balance = 20478 （期望 39000）
【切换间隔 1μs · 加锁】  balance = 39000 （期望 39000）
```

> **结论**：不能靠"跑出来结果不对"来判断要不要加锁——数据竞争是**时序相关**的，不加锁可能"看起来一切正常"。锁的必要性来自语言层面的保证：**线程切换可能发生在字节码边界**，只要共享变量存在"读-改-写"这种非原子操作，就必须加锁。（顺带一提，Python 3.13 起有实验性的 free-threaded 无 GIL 版本，竞争会变得更容易出现。）

### GIL：为什么多线程跑不满多核

Python 的线程虽然是真正的线程，但在解释器执行代码时有一个 **GIL（Global Interpreter Lock，全局解释器锁）**：任何 Python 线程执行前必须先获得 GIL，所以**多线程在 Python 中只能交替执行**，无法真正并行。

我实测了一下（同一台机器，16 核，4 个 CPU 密集任务，先预热再计时）：

```text
串行 4 次              : 1.22 秒
4 线程（受 GIL 限制）  : 1.26 秒（1.04 倍）
4 进程（含创建开销）   : 0.51 秒（0.42 倍）
```

4 个线程和串行几乎一样快（1.04 倍），说明**多线程一点并行都没赚到**；4 个进程则快了 2 倍多——因为**每个进程有各自独立的 GIL**。

所以：**Python 不能靠多线程实现多核任务，但可以通过多进程实现多核任务。**

> 多线程编程本身模型复杂，容易发生冲突，必须用锁隔离，还要小心死锁；这也是"能用多进程就别硬上多线程"的原因之一。

### ThreadLocal

在多线程环境下，每个线程都有自己的数据。一个线程使用自己的**局部变量**比使用全局变量好——不会影响其他线程，而全局变量必须加锁。但局部变量在函数调用的时候一层层传递很麻烦，这时可以用 `ThreadLocal`：

```python
import threading

local_school = threading.local()      # 创建全局 ThreadLocal 对象

def process_student():
    std = local_school.student        # 获取当前线程关联的 student
    print('Hello, %s (in %s)' % (std, threading.current_thread().name))

def process_thread(name):
    local_school.student = name       # 绑定 ThreadLocal 的 student
    process_student()

t1 = threading.Thread(target=process_thread, args=('Alice',), name='Thread-A')
t2 = threading.Thread(target=process_thread, args=('Bob',), name='Thread-B')
t1.start()
t2.start()
t1.join()
t2.join()
```

实测输出：

```text
Hello, Alice (in Thread-A)
Hello, Bob (in Thread-B)
```

创建一个全局的 `ThreadLocal` 对象后，每个线程都可以对它读写自己的属性，**互不影响**：`local_school.student` 在 Thread-A 里是 `Alice`，在 Thread-B 里是 `Bob`，不用在函数之间层层传参。

`ThreadLocal` 最常用的地方就是**为每个线程绑定一个数据库连接、HTTP 请求、用户身份信息**等——这样一个线程调用到的所有处理函数都能方便地访问这些资源。

## 多任务的取舍

实现多任务通常是一个 Master 负责分配任务、多个 Worker 负责执行任务。

**多进程：**

- 优点是**稳定性高**：一个子进程崩溃了，不会影响主进程和其他子进程；
- 缺点是**创建进程代价大**：Unix/Linux 下用 fork 调用代价尚可接受，Windows 下创建进程开销巨大；另外操作系统能同时运行的进程数有限（内存和 CPU 都是限制）。

**多线程：**

- 启动、切换的开销比进程小（所以"看起来快一点"），但**任何一个线程挂掉都可能造成整个进程崩溃**；
- 而且 CPU 密集任务下受 GIL 限制，多线程并不会更快（见上面的实测）。

**共同的规律**：不管是多进程还是多线程，**数量变多都会降低效率**，因为要支付切换任务的额外开销。

### 计算密集型 vs IO 密集型

是否采用多任务，还要看任务的类型：

| 任务类型 | 特点 | 建议 |
| --- | --- | --- |
| **计算密集型** | 要进行大量计算、消耗 CPU 资源 | 同时进行的数量应当**等于 CPU 的核心数**（多了只会增加切换开销） |
| **IO 密集型** | 涉及网络、磁盘 IO，大部分时间在**等待** IO 完成 | 任务越多 CPU 效率越高，但也有上限；Web 应用大多属于这一类 |

- 对计算密集型任务来说，**Python 这类脚本语言本身就不合适**（代码运行效率低）。真想加速，得靠 C 扩展、NumPy 这类把计算下沉到 C 的库，或者直接用 C/C++/Rust 写；
- 对 IO 密集型任务来说，花在 CPU 上的时间很少，**脚本语言反而是首选**——用多线程/多进程把等待的时间重叠起来就够了。

### 异步 IO 与协程

由于 CPU 和 IO 之间的速度差距巨大，单任务会有大部分时间在等待 IO，导致后续任务无法并发执行——所以我们需要多进程或多线程。

现代操作系统支持**异步 IO**：如果充分利用它，就可以用**单进程单线程**模型来执行多任务，这种模型称为**事件驱动模型**。Nginx 就是支持异步 IO 的 Web 服务器，在单核 CPU 上采用单进程模型就能高效支持多任务。

在 Python 里，单线程的异步编程模型称为**协程**。

## 分布式进程

`multiprocessing` 模块不但支持多进程，其中的 `managers` 子模块还支持把多进程**分布到多台机器**上：一个服务进程作为调度者，把任务分布到其他多个进程中，依靠网络通信。

服务进程负责启动 `Queue`，把 `Queue` 注册到网络上，然后往 `Queue` 里写入任务：

```python
# task_master.py

import random, time, queue
from multiprocessing.managers import BaseManager

task_queue = queue.Queue()
result_queue = queue.Queue()

class Queuemanager(BaseManager):
    pass
def get_task_queue():
    return task_queue
def get_result_queue():
    return result_queue
Queuemanager.register('get_task_queue', callable= get_task_queue)
Queuemanager.register('get_result_queue',callable= get_result_queue)

if __name__ == '__main__':
    manager = Queuemanager(address= ('127.0.0.1', 5000), authkey= b'abc')
    manager.start()
    task = manager.get_task_queue()
    result = manager.get_result_queue()

    for i in range(10):
        n = random.randint(0, 10000)
        print('Put task %d...' %n)
        task.put(n)

    print('Try get results.')
    for i in range(10):
        r = result.get(timeout= 10000)
        print('Result: %s' %r)

    manager.shutdown()
    print('Master exit.')

```
不使用lambda的原因是：

在Windows上无法使用lambda匿名函数作为callable参数的原因是因为在Windows上，需要通过pickle模块对对象进行序列化和反序列化，而lambda函数无法被正确地序列化。因此，在这种情况下，需要显式地定义一个函数来作为callable参数，以确保在进程之间正确地传递和执行任务。

需要添加__main__的原因：

在使用`multiprocessing`模块时出现了进程启动顺序的问题导致的。在Python中，特别是在Windows系统上，当使用`multiprocessing`模块创建子进程时，需要确保主模块（包含`if __name__ == '__main__':`的模块）在启动子进程之前进行适当的初始化。

另一台机器上运行 worker：

```python
# task_worker.py

import time, sys, queue
from multiprocessing.managers import BaseManager

# 创建类似的 QueueManager:
class QueueManager(BaseManager):
    pass

# 由于这个 QueueManager 只从网络上获取 Queue，所以注册时只提供名字:
QueueManager.register('get_task_queue')
QueueManager.register('get_result_queue')

# 连接到服务器，也就是运行 task_master.py 的机器:
server_addr = '127.0.0.1'
print('Connect to server %s...' % server_addr)
# 端口和验证码注意保持与 task_master.py 设置的完全一致:
m = QueueManager(address=(server_addr, 5000), authkey=b'abc')
# 从网络连接:
m.connect()
# 获取 Queue 的对象:
task = m.get_task_queue()
result = m.get_result_queue()
# 从 task 队列取任务,并把结果写入 result 队列:
for i in range(10):
    try:
        n = task.get(timeout=1)
        print('run task %d * %d...' % (n, n))
        r = '%d * %d = %d' % (n, n, n * n)
        time.sleep(1)
        result.put(r)
    except queue.Empty:            # 注意：导入的是小写的 queue 模块，异常是 queue.Empty
        print('task queue is empty.')
# 处理结束:
print('worker exit.')
```

运行顺序：先启动 master，等 master 发送完任务、开始等待 result 队列时，再启动 worker。

几个要点：

- `Queue` 对象存储在 master 的进程里；`Queue` 能通过网络访问，是通过 `QueueManager` 实现的——由于 `QueueManager` 管理的不止一个 `Queue`，所以要给每个 `Queue` 的网络调用接口起个名字（比如 `get_task_queue`）；
- 在分布式环境下，往 `Queue` 里添加任务**不能直接操作原始的 `task_queue`**，必须通过 `manager.get_task_queue()` 获得的 `Queue` 接口；
- `authkey` 验证码是为了保证两台机器正常通信，不被其他机器恶意干扰；
- `Queue` 用来传递任务和接收结果，**每个任务的描述数据量要尽量小**：比如发送一个处理日志文件的任务，传日志文件的完整路径即可，由 Worker 进程自己去共享磁盘上读文件。
