# 大数据体系学习笔记

> 学习主线：大数据解决**存、算、管、用**四个核心问题。前四节讲整体体系（对应各自主题），数据中台是"管"与"用"的桥梁，后半部分为打基础的概念串讲（数据库 → 数仓 → ETL → 数据湖 → 湖仓一体）。

## 什么是大数据

- 大数据是针对**海量数据**处理的一套**完整技术体系**。
- 主要解决四个核心问题：
  - **存**（存储）：如 HDFS、对象存储
  - **算**（计算）：如 Spark、Flink
  - **管**（管理）：如元数据管理、资源调度
  - **用**（应用）：如分析、报表、AI

## 存储体系（存）

- 数据按用途分层存放：
  - **热数据**：上游业务数据库
  - **分析数据**：数据仓库
  - **原始数据**：数据湖
- 数据湖早期经典的底层存储介质是 **HDFS**。

### HDFS（Hadoop Distributed File System，分布式文件系统）

- 把文件切成默认 **128MB** 的数据块（block），分散存到**几千台普通服务器**上。
- 每个数据块存 **3 个副本**（默认副本因子 replication factor=3，可配置），放到不同机器（容错）；典型策略是本地 1 份 + 同机架 1 份 + 跨机架 1 份。
- 角色分工：
  - **NameNode（主管）**：记录索引信息（元数据）
  - **DataNode（储物柜）**：存储数据块
- 读写流程：先问 **NameNode** 找位置，再去对应的 **DataNode** 读写。

### 数据湖的管理系统

- HDFS 本身提供**基础的文件系统管理**（命名空间、文件-块映射、简单权限），但缺少**湖级治理能力**（统一数据目录、血缘、细粒度权限），因此数据湖在 HDFS 之上增加了一套管理系统：
  - **数据接入工具**：负责把数据拉入湖里
  - **元数据管理**：记录湖里有什么数据、存在哪里
  - **数据目录**：给数据分类、打标签，以及细粒度的权限控制
- **趋势**：行业已由自建 HDFS 集群转向**云对象存储**（如 S3、OSS）——对象存储成为统一底座后，正是 Delta Lake / Apache Iceberg / Apache Hudi 这类表格式引擎在其之上补上管理能力（见下文"湖仓一体"一节）。

## 计算体系（算）

- **思路与分布式存储一致**：数据太多单台服务器扛不住，先把全量数据拆分成一个个小分片，分给多台服务器处理，最后把结果聚合起来。
- 核心是两个函数：
  - **map() 函数**：告诉机器本地数据的每行要怎么处理
  - **reduce() 函数**：告诉系统所有机器的局部结果怎么汇总
  - 这一套计算框架就是 **MapReduce**。
- **数据本地性（data locality）**：计算分发到存数据的机器上执行，减少网络传输——与存储体系的分片思想一脉相承。
- **shuffle（洗牌）**：map 输出后要按 key 分区、排序，reduce 再跨机器拉取属于自己的分区——中间结果落盘主要发生在这里。
- **痛点**：每次中间运算结果都会写入磁盘，严重拖慢速度。

### YARN（Yet Another Resource Negotiator，资源调度）

- 全称 Yet Another Resource Negotiator（"又一个资源协调器"）。
- 作用：管理分配 Map 任务应该去**哪一台服务器节点**执行——是**服务器节点**和**运算任务**之间的**中间层**。
- 核心抽象：**容器（Container）**——把每个计算任务所需的资源抽象为容器，容器本质上就是**被限制了 CPU 和内存的 JVM 虚拟机进程**。
- 三个角色：
  - **ResourceManager（RM）**：集群资源的总调度者（全局一个），决定资源分给谁
  - **NodeManager（NM）**：每台节点一个，管理本机的容器，定期向 RM 汇报资源情况
  - **ApplicationMaster（AM）**：每个应用一个，为该应用的任务申请容器、协调任务执行
- 作业流程：提交任务 → RM 分配一个容器启动 AM → AM 按需向 RM 申请更多容器 → 任务在对应节点的 NM 上启动容器执行 → 全部完成，AM 退出。
- **通用性**：YARN 不只服务 MapReduce，Spark、Flink 等计算框架都能跑在 YARN 上（共用统一资源池）。

### Spark 与 Flink（MapReduce 的改进与实时方案）

- **Spark 的优化**：把中间结果放在**内存**里计算，内存不够再使用磁盘——显著提速，是现在**离线批量计算**的主流。
  - 更本质的优化是 **DAG 调度**：同一作业内减少 shuffle 次数（MR 每一步都 shuffle，Spark 一次作业只洗牌一次）。
- **实时场景**：业务需要处理实时数据时，MapReduce 和 Spark 不够用，转而使用 **Flink**——流计算框架，**来一条就立刻处理一条**。
  - Spark 本质是**微批（micro-batch）**，Flink 才是真正的逐条流式处理。
  - Flink 的关键特性：低延迟、状态管理、checkpoint 容错（实现 exactly-once）。

### Hive（Hadoop 上的数据仓库工具）

- 把 HDFS 上的数据映射成**表**，用 **SQL** 查询（类 MySQL 语法），底层自动把 SQL 翻译成 MapReduce/Spark 任务执行。
- 本质上是 **SQL 与 HDFS（Hadoop）之间的中间层**：上层解析 SQL，下层调度计算任务。
- 元数据（表结构、数据位置）存在 **Metastore**（如 MySQL）中。
- 对应"数据仓库"一节的概念：Hive 就是 Hadoop 生态里的数仓实现，适合**离线批量分析**。

### HBase（分布式列存储数据库）

- **定位**：海量数据的**随机读写**数据库（NoSQL），基于 HDFS，支持百亿行级别的在线读写。
- **模型**：列式宽表，按行键（row key）点查，稀疏存储（空列不占空间）。
- **场景**：海量在线业务数据（订单、轨迹、日志明细等）。
- **与 Redis 的区别**（同为 NoSQL 但定位不同）：
  - Redis：**内存缓存**，微秒级延迟，容量受内存限制，管"热得快"的数据
  - HBase：**磁盘存储**（底层 HDFS），毫秒~百毫秒级，容量大能存冷数据
  - 两者互补：Redis 在前缓存热点，HBase 在后存全量

## 管理体系（管）

- **任务调度**：解决"任务怎么按时进行"——定时触发，例如 **Airflow** 工具，可以**自动编排所有任务的依赖关系**。
- **数据治理**：解决"数据怎么不出错"——保证数据的**质量**和**安全**，例如：
  - 统一数据统计口径
  - 监控数据异常值
  - 管控数据权限
- **数据血缘（lineage）**：记录数据从哪来、被谁加工、流到哪里——排查数据问题靠它追溯来源，与前面"元数据管理"呼应。
- **数据安全**：不止权限管控，还包括数据**分级分类**、敏感数据**脱敏**、访问**审计**。
- **数据质量维度**：完整性、准确性、一致性、及时性——"监控异常值"只是其中之一。

## 应用体系（用）

- 所有技术最终都要**实现于业务**；应用侧就是大数据的**对外接口**。
- 一般分两类：
  - **基础应用**：BI 报表、数据大屏
  - **高级应用**：推荐系统、风控系统
- **BI 报表 vs 数据大屏**：BI 面向内部人员自助分析（即席查询、报表，如 Tableau、帆软 FineBI）；数据大屏面向领导/对外展示，偏实时监控与可视化呈现。
- **推荐系统构成**：离线训练模型 + 实时特征更新——正好用上"算"一节的体系（Spark 离线、Flink 实时）。
- **风控系统**：规则引擎 + 机器学习模型，通常依赖 Kafka + Flink 实时链路。
- **对外接口不限于两类应用**：还有数据服务层——指标服务、数据 API（数据服务中台）。

## 数据中台

- **背景**：企业级管理问题——不同部门之间存在**数据孤岛**和**重复开发**。
- **解决思路**：发明**数据中台管理体系**。
- **核心**：数据**资产化**和**服务化**——把用户常用指标加工成**标准化的数据资产**，封装为 **API 接口**，让数据变成可以直接被调用的**服务**。
- **串联位置**：数据中台是"管"与"用"之间的**桥梁**——把治理好的数据资产化，再以服务形式支撑应用；"统一统计口径"（管一节）正是中台加工标准指标的过程，两者呼应。
- **分层结构**：数据平台（底层）→ 数据中台（资产化/服务化）→ 业务应用；中台在中间层，避免各业务部门重复造轮子。
- **具体组成**：指标中心、标签体系（用户画像）、数据服务层（API 网关）。
- **与数仓的关系**：中台建立在数仓之上——数仓解决"数据怎么组织"，中台解决"数据怎么变成服务"。
- **现状提醒**：数据中台概念近年有降温（成本高、落地难），不少企业转向"湖仓一体 + 数据服务"的轻量组合。

## 数据库特点

- 支持**自动备份**，降低数据丢失风险。
- 支持**多人协作**，多用户并发读写。
- 常用数据库：**MySQL**、**Oracle**、**PostgreSQL**。

## 行式存储

- 数据库把数据按**表**组织：一行一条完整记录，一列一个属性。
- 磁盘上，一条记录的所有字段**紧挨着存放**，一行一行往下存。
- 这种存储方式称为**行式存储（row-oriented storage）**。

```text
磁盘布局示意：

表: 用户信息(姓名, 年龄, 城市)
第1行: | 张三 | 28 | 北京 |
第2行: | 李四 | 35 | 上海 |
第3行: | 王五 | 42 | 广州 |
   ↑ 每条记录的字段连续存放
```

- 与列式存储（column-oriented storage）的对比：见下节。

## 列式存储与数据仓库

- **处理数据**与**分析数据**是两种完全不同的需求：日常事务处理关心单条记录的读写，分析关心大量数据的聚合统计。
- 因此把**分析数据单独拿出来**，称为**数据仓库（data warehouse）**。
- **数据仓库普遍使用列式存储（column-oriented storage）**——把同一列的数据存放在一起（列式存储并非数据仓库专属，其他场景也可使用）。

```text
同一张表，两种存法：

行式存储：每行字段连续
| 张三 | 28 | 北京 | | 李四 | 35 | 上海 | ...

列式存储：每列数据连续
张三 | 李四 | 王五 ...   ← 姓名列
28   | 35   | 42   ...   ← 年龄列
北京 | 上海 | 广州 ...   ← 城市列
```

- **为什么分析场景普遍选列式**：
  1. 分析通常只取**少数列**做聚合（如 `SUM(age)`），列式存储可以**只读相关列**，跳过无关字段，减少磁盘 IO。
  2. 同一列字段**类型相同**，压缩率更高。
- 与行式存储的对比：行式适合按行读写（事务处理），列式适合按列聚合分析（数据仓库）。
- 常用列式存储产品：**ClickHouse、Apache Doris、StarRocks**；分析型文件格式：**Parquet、ORC**。

## ETL：抽取-转换-加载

- **ETL = Extract（抽取）→ Transform（转换）→ Load（加载）**，完成这一流程的工具称为 **ETL 工具**。
- **Extract（抽取）**：通过数据库的**标准查询接口**，从分散的业务数据库抽取数据。
- **Transform（转换）**：主要是**脏数据清洗**——统一格式、去重、把空值补充为默认值等。
- **Load（加载）**：将清洗后的数据按分析主题写入数据仓库。
- **数据库 vs 数据仓库**：
  - 数据库：数据按表存储。
  - 数据仓库：按**分析主题**（如订单、用户）组织数据，同时有**加工分层**（如 ODS → DWD → DWS → ADS）；底层仍然是正常表格，分析常用的**宽表**一般由 ETL 提前物化（预先 JOIN/聚合存好），而不是每次分析时现联合。
- **整体链路**：分散的业务数据库 → ETL 抽取 → 清洗（Transform）→ 按分析主题 Load 入数据仓库。

## 数据湖

- 把所有**原始数据**放在一起，称为**数据湖（data lake）**；集中存放**各种格式**的数据（结构化、半结构化、非结构化），核心特征是以低成本集中存储海量数据。
- 特点是**先存储、再处理**——对应 **schema-on-read（读时定义模式）**：存的时候不管格式，读的时候才解析；与数仓的 **schema-on-write（写时定义模式，先清洗再入库）** 正相反。
- **缺点**：没有统一管理，数据质量、元数据管理薄弱（容易变成 data swamp）。

## 湖仓一体（Lakehouse）

- 基于数据仓库与数据湖的特点创建：把湖和仓库**彻底打通**，让数据和元数据**按需流动**。
- **核心思想**：不是"热数据放仓、冷数据放湖"的分开存储，而是所有数据**统一存放在低成本存储（湖）上**，直接在其上提供**仓库能力**——通过表格式引擎获得事务、元数据管理、性能优化等；数仓与湖**共用同一份存储和元数据**，数据本身不用在湖和仓之间搬运。
- 处理流程：
  1. 所有原始数据先**统一入湖**。
  2. 清洗后分为**热数据**（常用）与**冷数据**（不常用）。
  3. 热数据提供仓库级访问能力，冷数据放**低成本存储归档**；同一底座上**冷热数据可联合运算**。
  4. 生成的结果同时支持存入数据仓库和数据湖。
- 底层依靠**表格式引擎（table format）**实现，主流开源三件套：**Delta Lake、Apache Iceberg、Apache Hudi**。
