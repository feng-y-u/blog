## 错误处理：try...except...finally

当认为某段代码可能会出错时，就可以用 `try` 来运行这段代码：

```python
try:
    print('try...')
    r = 10 / 0              # 这里一定会出错
    print('result:', r)     # 出错后，这一行不会执行
except ZeroDivisionError as e:
    print('except:', e)     # 接住这个异常对象并打印
finally:
    print('finally...')     # 不管有没有出错都会执行
print('END')                # try 语句之外的代码，继续执行
```

实际输出：

```text
try...
except: division by zero
finally...
END
```

执行流程：

- 如果代码块执行出错，**后续代码不会执行**，而是直接跳转到错误处理代码 `except` 语句块；
- 执行完 `except` 后，如果还有 `finally` 语句块，则执行 `finally` 语句块（**finally 一定会被执行**）；
- `try` 语句之外的代码继续正常执行——上面例子里最后的 `END` 就打印出来了。

### 多种错误类型

错误有很多种类型，发生不同类型的错误，应该由不同的 `except` 语句块处理：

```python
def divide(s):
    try:
        r = 10 / int(s)          # int('a') 抛 ValueError；除以 0 抛 ZeroDivisionError
    except ValueError as e:
        print('ValueError:', e)
    except ZeroDivisionError as e:
        print('ZeroDivisionError:', e)
    else:
        print('没有出错，结果是:', r)   # 只有没异常时才走到这里
    finally:
        print('finally...')

divide('a')
divide('0')
divide('2')
```

实际输出：

```text
ValueError: invalid literal for int() with base 10: 'a'
finally...
ZeroDivisionError: division by zero
finally...
没有出错，结果是: 5.0
finally...
```

> **注意 `else` 的位置**：`try → except → else → finally` 的顺序是固定的——`else` 在 `except` 之后、`finally` 之前，并且只在 **try 块没有异常**时执行。
> 它的用处是把"容易出错的代码"和"没出错才做的后续操作"分开：如果全塞进 `try` 里，后面那句本该安全的代码一旦出错，也会被自己的 `except` 抓走，你会误以为是前面那段代码的问题。

### 错误是 class，父类能捕获子类

Python 的错误也是 class，所有错误都继承自 `BaseException`。所以使用 `except` 时要注意：**它不但捕获该类型的错误，还会把它的子类一起捕获**。

```python
try:
    raise UnicodeError('bad encoding')
except ValueError as e:
    print('被 ValueError 捕获:', type(e).__name__)
except UnicodeError as e:
    print('被 UnicodeError 捕获（永远到不了这里）')
```

实际输出：

```text
被 ValueError 捕获: UnicodeError
```

因为 `UnicodeError` 是 `ValueError` 的子类，所以第二个 `except` 永远捕获不到错误——**多个 `except` 要"具体的（子类）写前面、笼统的（父类）写后面"**，否则后面的分支就是死代码。

常见的错误类型和继承关系见[官方文档](https://docs.python.org/3/library/exceptions.html#exception-hierarchy)。

### 调用栈：错误会一层层上报

如果错误没有被捕获，就会一直上抛，最后打印出完整的调用栈：

```python
# err.py
def foo(s):
    return 10 / int(s)

def bar(s):
    return foo(s) * 2

def main():
    bar('0')

main()
```

```text
$ python3 err.py
Traceback (most recent call last):
  File "err.py", line 10, in <module>
    main()
  File "err.py", line 8, in main
    bar('0')
  File "err.py", line 5, in bar
    return foo(s) * 2
  File "err.py", line 2, in foo
    return 10 / int(s)
ZeroDivisionError: division by zero
```

错误一层层上报，一直到根源处的错误源头 `ZeroDivisionError: division by zero`。

> **traceback 要从下往上看**：最下面一行是错误类型和原因，往上是它经过的每一层调用（`foo` → `bar` → `main` → 模块顶层）。

### 记录错误（logging）

用内置的 `logging` 模块可以把错误记录下来：

```python
import logging

def foo(s):
    return 10 / int(s)

def bar(s):
    return foo(s) * 2

def main():
    try:
        bar('0')
    except Exception as e:
        logging.exception(e)      # 记录完整的 traceback

main()
print('END')
```

实际输出：

```text
ERROR:root:division by zero
Traceback (most recent call last):
  File "err_logging.py", line 11, in main
    bar('0')
  File "err_logging.py", line 7, in bar
    return foo(s) * 2
  File "err_logging.py", line 4, in foo
    return 10 / int(s)
ZeroDivisionError: division by zero
END
```

打印完错误信息后程序继续执行（输出了 `END`），而通过配置，logging 还可以把错误记录到日志文件里。

> **注意**：让程序继续执行的是 `except`，不是 `logging`。logging 只负责"记录"，它不会让异常消失——如果异常没有被捕获，即使 import 了 logging，程序照样会终止。

### 抛出错误（raise）

错误就是 class，捕获一个错误就是捕获到该 class 的一个实例；错误是**有意创建并抛出**的。要抛出错误，首先根据需要定义一个错误的 class、选好继承关系，然后用 `raise` 语句抛出一个错误的实例：

```python
class FooError(ValueError):
    pass

def foo(s):
    n = int(s)
    if n == 0:
        raise FooError('invalid value: %s' % s)
    return 10 / n

foo('0')
```

```text
$ python3 err_raise.py
Traceback (most recent call last):
  File "err_raise.py", line 10, in <module>
    foo('0')
  File "err_raise.py", line 7, in foo
    raise FooError('invalid value: %s' % s)
FooError: invalid value: 0        # 这就是我们定义的错误
```

- 自定义异常最好**继承一个内置异常**（如上例继承 `ValueError`），这样调用方用 `except ValueError` 就能一并接住它；
- 尽量使用 Python 内置的错误类型；
- `raise` 语句如果不带参数，就会把当前错误原样抛出；在 `except` 中 `raise` 一个 Error，可以把一种错误类型转换为另一种错误类型。

## 调试

有的 bug 很复杂，我们需要知道出错时哪些变量的值是对的、哪些是错的，因此需要一整套调试程序的手段。

### 断言 assert

```python
def foo(s):
    n = int(s)
    assert n != 0, 'n is zero!'
    return 10 / n

def main():
    foo('0')
```

如果 `assert` 后面跟的表达式结果为 False，`assert` 语句本身会抛出 `AssertionError`：

```text
$ python err.py
Traceback (most recent call last):
  ...
AssertionError: n is zero!
```

启动 Python 解释器时，加上命令行参数 `-O` 可以关闭 assert——assert 被整条删掉后，错误就变成了除零：

```text
$ python -O err_assert.py
Traceback (most recent call last):
  ...
ZeroDivisionError: division by zero
```

> **结论**：既然 assert 可以被 `-O` 关掉，就**不能用它做参数校验**。它适合"这不可能发生，一旦发生说明我代码写错了"的自检；要拦住非法输入，得用 `raise ValueError('n must not be zero')`。

### logging

与 assert 相比，logging **不会抛出错误**，而且可以输出到文件：

```python
import logging
logging.basicConfig(level=logging.INFO)

s = '0'
n = int(s)
logging.info('n = %d' % n)
print(10 / n)
```

logging 允许指定记录信息的级别，有 debug、info、warning、error 等几个级别：

> 标准级别从低到高为：`DEBUG`(10) < `INFO`(20) < `WARNING`(30) < `ERROR`(40) < `CRITICAL`(50)

实际输出（注意 `logging.debug` 那条看不到）：

```text
$ python log_levels.py
INFO:root:这条看得到
WARNING:root:这条也看得到
```

因为 **logging 的默认级别是 WARNING**，所以要先 `basicConfig(level=logging.INFO)` 才能看到 INFO 级别的日志。日志输出到 **stderr**；logging 还可以通过简单的配置，把一条语句同时输出到不同的地方（屏幕、文件等）。

### pdb

在命令行添加 `-m pdb` 参数启动时，pdb 会定位到下一步要执行的代码。常用命令：

| 命令 | 作用 |
| --- | --- |
| `l` | 查看代码（list 的缩写，是小写字母 L，不是数字 1） |
| `n` | 单步执行（next） |
| `p 变量名` | 查看变量的值（print） |
| `c` | 继续运行（continue） |
| `q` | 退出（quit） |

也可以在代码内部 import pdb，用 `pdb.set_trace()` 设置断点：运行到这一行会自动暂停并进入 pdb 调试环境。

```python
# err.py
import pdb

s = '0'
n = int(s)
pdb.set_trace()     # 运行到这里会自动暂停
print(10 / n)
```

> **小结**：定位一个具体的 bug，IDE 的图形化 debug 更快；pdb 的价值在于没有图形界面时（比如在服务器上）也能调试。

## 单元测试（unittest）

TDD：Test-Driven Development，测试驱动开发。**单元测试**用来对一个模块、一个函数或者一个类进行正确性检验。

比如测试函数 `abs()`：

1. 输入正数，期待返回值与输入相同；
2. 输入负数，期待返回值与输入相反；
3. 输入 0，期待返回值为 0；
4. 输入非数值类型（比如 `None`），期待抛出 `TypeError`。

把这些测试放到一个测试模块里，就是一个完整的单元测试。单元测试通过后，说明这个函数可以正常工作；之后就算我们对 `abs()` 做了修改，只需要再跑一遍单元测试，能通过就说明修改不会对原有行为产生影响。

### 被测代码：一个能用属性访问的 Dict

```python
# mydict.py
class Dict(dict):
    def __init__(self, **kw):
        super().__init__(**kw)

    def __getattr__(self, key):
        # 用 d.key 访问属性时，Python 常规属性查找失败后，会调用 __getattr__
        try:
            return self[key]
        except KeyError:
            raise AttributeError(r"'Dict' object has no attribute '%s'" % key)

    def __setattr__(self, key, value):
        # 执行 d.key = 'value' 时，Python 会调用 d.__setattr__('key', 'value')
        self[key] = value
```

（`__getattr__` 为什么会这样写，见"定制类"那篇；在这里它只是被测对象。）

### 测试代码

编写单元测试需要引入 Python 自带的 `unittest` 模块，编写 `mydict_test.py`：

```python
import unittest

from mydict import Dict


class TestDict(unittest.TestCase):

    def test_init(self):
        d = Dict(a=1, b='test')
        self.assertEqual(d.a, 1)
        self.assertEqual(d.b, 'test')
        self.assertTrue(isinstance(d, dict))

    def test_key(self):
        d = Dict()
        d['key'] = 'value'
        self.assertEqual(d.key, 'value')

    def test_attr(self):
        d = Dict()
        d.key = 'value'
        self.assertTrue('key' in d)
        self.assertEqual(d['key'], 'value')

    def test_keyerror(self):
        d = Dict()
        with self.assertRaises(KeyError):
            value = d['empty']

    def test_attrerror(self):
        d = Dict()
        with self.assertRaises(AttributeError):
            value = d.empty


if __name__ == '__main__':
    unittest.main()
```

规则：

- 测试类从 `unittest.TestCase` 继承；
- **以 `test` 开头的方法**才是测试方法，不以 `test` 开头的方法不被认为是测试方法，测试的时候不会被执行；
- `unittest.TestCase` 提供了很多内置的条件判断：`assertEqual()`、`assertTrue()`、`assertRaises()` 等等。

> **注意缩进**：同一个代码块里不能混用 Tab 和空格，Python 3 会直接报错：
> `IndentationError: unindent does not match any outer indentation level`。统一用 4 个空格就没这个问题。

### 运行单元测试

第一种方法：在单元测试文件最后加上两行：

```python
if __name__ == '__main__':
    unittest.main()
```

第二种方法：使用命令行参数：

```text
$ python -m unittest mydict_test
.....
----------------------------------------------------------------------
Ran 5 tests in 0.000s

OK
```

**每有一个点，就代表一个测试通过。**

```text
$ python -m unittest mydict_test.TestDict.test_attr     # 指定单个测试方法
.
----------------------------------------------------------------------
Ran 1 test in 0.000s

OK

$ python -m unittest mydict_test -k attr                # 筛选名字里含 attr 的测试
..
----------------------------------------------------------------------
Ran 2 tests in 0.000s

OK
```

参数 `-v` 能打印出具体执行的测试方法：

```text
$ python -m unittest mydict_test -v
test_attr (mydict_test.TestDict.test_attr) ... ok
test_attrerror (mydict_test.TestDict.test_attrerror) ... ok
test_init (mydict_test.TestDict.test_init) ... ok
test_key (mydict_test.TestDict.test_key) ... ok
test_keyerror (mydict_test.TestDict.test_keyerror) ... ok

----------------------------------------------------------------------
Ran 5 tests in 0.000s

OK
```

测试失败时显示 `F`，并给出"期望 vs 实际"：

```text
$ python -m unittest mydict_test_fail
F
======================================================================
FAIL: test_wrong_expectation (mydict_test_fail.TestDictFail.test_wrong_expectation)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "mydict_test_fail.py", line 8, in test_wrong_expectation
    self.assertEqual(d.a, 2)
AssertionError: 1 != 2

----------------------------------------------------------------------
Ran 1 test in 0.003s

FAILED (failures=1)
```

### setUp 与 tearDown

单元测试中有两个特殊的 `setUp()` 和 `tearDown()` 方法，这两个方法会分别在**每调用一个测试方法的前后**被执行：

```text
$ python setup_order.py
   --> setUp
   --> test_a
   --> tearDown
   --> setUp
   --> test_b
   --> tearDown
```

## 文档测试（doctest）

doctest 把"写在文档字符串里的示例代码"直接当成测试运行。

**文档字符串**是 `'''三引号字符串'''`，它不是普通注释，而是 Python 对函数、类、模块提供的正式文档：

```python
def abs_(n):
    """
    求绝对值。

    >>> abs_(1)
    1
    >>> abs_(-1)
    1
    >>> abs_(0)
    0
    """
    return n if n >= 0 else -n
```

`>>>` 后面是**要执行的代码**，紧跟着的那几行是**期望输出**：doctest 会把代码真的执行一遍，再把真实输出与期望输出逐字比较。

使用 doctest 测试异常：

```python
    >>> d['empty']
    Traceback (most recent call last):
        ...
    KeyError: 'empty'
```

可以使用 `...` 省略中间的错误信息。

实际运行（`-v` 会打印每一条被执行的示例）：

```text
$ python -m doctest -v mydict_doctest.py
Trying:
    abs_(1)
Expecting:
    1
ok
Trying:
    abs_(-1)
Expecting:
    1
ok
Trying:
    abs_(0)
Expecting:
    0
ok
Trying:
    d = Dict(a=1)
Expecting nothing
ok
Trying:
    d.a
Expecting:
    1
ok
Trying:
    d['empty']
Expecting:
    Traceback (most recent call last):
        ...
    KeyError: 'empty'
ok
2 items passed all tests:
   3 tests in mydict_doctest.abs_
   3 tests in mydict_doctest.use_dict
6 tests in 5 items.
6 passed.
Test passed.
```

如果期望写错了，doctest 会把"期望"和"实际"并排显示：

```text
$ python -m doctest mydict_doctest_bad.py
**********************************************************************
File "mydict_doctest_bad.py", line 3, in mydict_doctest_bad.abs_
Failed example:
    abs_(1)
Expected:
    -1
Got:
    1
**********************************************************************
1 item had failures:
   1 of   1 in mydict_doctest_bad.abs_
***Test Failed*** 1 failure.
```

这就是 doctest 最省事的地方：**文档里的例子顺便就是测试**。

## 小结：四种"发现问题"的手段

| 手段 | 解决什么 | 会不会打断程序 |
| --- | --- | --- |
| `assert` | 开发期自检"这里不该出错" | 会（抛 AssertionError），但可能被 `-O` 关掉 |
| `logging` | 留下痕迹，事后追查 | 不会 |
| `pdb` | 停下来，一步步看现场 | 会（暂停） |
| `unittest` / `doctest` | 把期望固化，改代码后重复验证 | 会（失败时报告） |
